## Proposed moments

| Moment | Trigger and purpose | Proposed timing | Reduced-motion / accessible alternative |
| --- | --- | --- | --- |
| **01 Stay with the car** | Tap a car card: its photo expands into the workspace; supporting information arrives shortly after. Reverse on Back. Preserve vehicle ID, list position and return focus. | Photo 360 ms; supporting text 220 ms, beginning after 90 ms. | Immediate destination with the same car title, photo and explicit Back button. No flying photo. Fall back to this if layout/image measurement is unavailable. |
| **02 At your fingertips** | Select Inspection/Repairs/Handover: indicator slides while only the work content changes direction. The photo, car name and actions stay anchored. Tab state is retained. | Selector 260 ms; content 200 ms, travel 14 px in this scaled study. | Immediate panel replacement and selected-state change. Visible tab names, programmatic selected state, normal focus, no swipe dependency. |
| **02 Evidence feedback** | A locally saved photo settles into its evidence slot. No full-screen flash or camera shutter simulation. It acknowledges media attachment only. | 220 ms settle; optional 340 ms focus outline. | Immediate thumbnail plus persistent text. Photo attached, result selected, queued and server-verified upload remain separate states. |
| **03 A moment to remember** | After an owner-initiated delivery has actually been confirmed: a short headlight-inspired line draws around a key emblem. Content and navigation are immediately usable. | Lines 700 ms; emblem 420 ms; title 300 ms, concurrently. | Immediate completed record and static motif. No replay loop, confetti, audio, status-dependent wait or animation required to continue. |

Recommendation: apply 01 and 02 as the working motion language and keep 03 occasional, owner-facing and tied to a confirmed delivery. The existing journey car remains on the Garage journey filter; the hidden Night Drive remains a separate optional Easter egg. Neither should become a general transition or loading indicator.

The preview uses a completed-delivery sample independently of the unfinished inspection sample. It never bypasses actual business gates. A sample attached photo uses a neutral media icon and explicitly still needs an inspection result.

## Native implementation after approval

1. **Presentation owns motion.** Add shared duration/easing tokens and a motion-preference hook near the existing presentation components. Domain commands, repositories, permissions, audit records, media processing and API contracts do not import animation code. The existing app already uses React Native Animated, native-stack navigation, AccessibilityInfo and Expo Haptics; no new motion dependency is proposed yet.
2. **Do the frequent transition first.** Build a reusable focused-tab panel with interrupted animations cancelled, explicit panel identity and draft state owned above the animated subtree. Rapid tab switching must not reset work, replay network commands or disable useful controls. Define direction from tab order. Android/iOS Back, keyboard focus and screen-reader announcements stay consistent.
3. **Vehicle continuity is optional enhancement.** A presentation-only overlay can bridge measured card/destination image rectangles using translation, scale and opacity. Keep the selected vehicle ID authoritative in navigation. Never wait for an image download or animate a different car's cached photo. If navigation is interrupted, layout changes, media is absent or measurements fail, cancel and show the destination normally. On roomy tablets keep the list anchored and transition the detail pane instead of moving the whole screen. Prototype layout animation is illustrative; native implementation must avoid per-frame layout work.
4. **Evidence tells the truth.** Settle the thumbnail only after the existing durable local save succeeds. Use a queued indicator until server acknowledgement/verification; retain retry/error feedback. Never animate an inspection pass from a photo attachment. Preserve the required mobile-side Full HD maximum photos and 720p video processing unchanged.
5. **Milestones follow confirmed state.** Trigger the owner signature from a successful user-initiated delivery command response. Do not replay it when background sync, navigation restoration or duplicate retries observe the same delivered record. Use the existing durable command/event identity for deduplication where appropriate; decoration must never create a business command. Existing warranty/document/payment gates still apply.
6. **Accessibility and performance are acceptance requirements.** Default to reduced motion until preference is known, handle preference changes and cancellation, no continuous loops in work screens, no sound, no mandatory gesture, at least 48 dp native touch targets. One optional haptic only on a deliberate meaningful action and only where supported; no haptics in this HTML study. Use opacity/transform with the native driver where supported, avoid layout-affecting animation for routine navigation, and profile on the target Android hardware before accepting the timing. Honor OS reduced motion, English/Hindi, large text, VoiceOver/TalkBack, phone/tablet orientation and Android Back.

## Verification and remaining acceptance

The isolated Chrome review exercised both car transitions and focus return, tab/evidence persistence, usable content during delivery animation, manual and OS reduced motion, original asset loading, and horizontal layout at 1440×1040, 1024×768, 430×932 and 360×800. A separate offline check blocked HTTP/HTTPS requests and verified embedded dynamic images, interruption, keyboard tabs and that the open-car, attached-photo and completed-delivery actions fit vertically in both device preview modes at all four widths. No runtime exceptions were observed. Evidence: [browser verification](review/motion/browser-verification.json), [offline/height verification](review/motion/offline-verification.json), [car view](review/motion/01-car-desktop.png), [tablet tabs](review/motion/02-tabs-tablet.png), [delivery](review/motion/03-delivery-tablet.png).

Still pending: owner choice/approval, integration into the actual mobile app, performance profiling, device accessibility checks, native reduced-motion behavior, real draft/upload/command lifecycle verification, Android phone/tablet and iPhone/iPad acceptance. This work does not close UX-23 or any full-release gate. The prototype includes no real workflow, camera, API, account or marketing connection.
